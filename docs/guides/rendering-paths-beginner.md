## 先抓住区别

前向：绘制表面时就计算光照；延迟：先记录表面属性，再计算光照；
后处理：读取已经生成的图像和辅助数据，再生成处理后的图像。
它们并不互斥。一帧经常使用“不透明延迟 + 透明前向 + 后处理”。

先问三个问题：某个像素看见谁（可见性）、它有多亮（着色）、屏幕如何显示它（显示转换）。
深度测试帮助解决遮挡；材质、法线和光源参与着色；曝光、色调映射和显示编码处理显示问题。

## 一个红球和三盏灯

前向：红球的片元着色器读取材质、位置和法线，计算有关灯的贡献，写场景颜色。
延迟：先把红球可见表面的材质和法线等写入G-buffer；照明pass再读取这些信息和深度，求出颜色。
两者完全可以使用同一个BRDF。渲染路径不是材质模型，不决定必须用Phong还是PBR。

G-buffer不是几张重复的彩色照片，而是屏幕大小的“表面记录表”。
位置常通过深度重建，格式没有固定标准；图20.2还包含照明结果调试视图，
不能误以为所有引擎必须存八张相同的图。

延迟可能有利于组织大量光源和可见表面的着色，但增加存储、写入与读取成本。
假设每像素16字节，1080p约占33.2MB；60fps仅完整写一次约1.99GB/s，
不含照明读取和其他缓冲。这是教学估算，不是实际GPU耗时。
原书709页还指出，逐灯全屏读取的朴素延迟方法可能比前向慢。

普通单层G-buffer不足以记录玻璃后面的多层表面，所以透明常单独用前向处理。
透明排序、MSAA、多材质和带宽都必须纳入设计。Forward+把局部光源列表用于前向；
分块/聚类也能用于延迟，它们是光源剔除方式，不是互斥的三套标签。

## 后处理怎么接

一个示意流程是：场景着色 → HDR颜色 → 泛光等图像处理 → 曝光/色调映射 → 显示编码 → UI。
具体引擎的TAA、调色、透明和UI位置可能不同，应按依赖设计，不能照搬为强制顺序。
Bloom通常需要保留HDR亮度，先把2和20都截成1会丢掉亮度差别。
Gamma近似编码不是色调映射；颜色混合通常应在线性空间计算。

你的ShaderToy示例中：

```text
Common：共享函数，不输出图像
BufferA：体积步进 → RGB光照/自发光，alpha为自定义g光晕信号
BufferB iChannel0 ← A：RGB亮区提取，保留alpha
Image iChannel0 ← A；iChannel1 ← B：泛光/径向光束/暗角/调色等
```

这是体积渲染加后处理，不是延迟渲染。Channel是输入插槽，RGBA含义由作者约定。
Image读取B的mip2–5需要配置mipmap；多Buffer本身并不代表G-buffer。
可在外部ShaderToy依次令BL、RS、VG、SP为0，观察每个效果，避免一次改多个变量。
